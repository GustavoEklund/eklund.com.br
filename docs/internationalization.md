# Internationalization

Two languages, pt-BR (default) and en-US. Each has its own page, which is what lets the English one have a real canonical address: `/` is Portuguese and `/en/` is English (the same markup, with every default text written in English, so crawlers and social cards read English there). The copy each release leaves in a folder follows the same rule from its folder: `/1.1.0/` is Portuguese and `/1.1.0/en/` is English. In the browser the language still switches without a reload, and the address follows.

- **Which language:** the address says which page this is, and a page inside an `en/` folder is English. The inline script in the head of `index.html` decides, before the first paint, whether a visitor who opened `/` goes to `/en/` (it acts only at the root, so the copy of a version leaves the visitor on the page they opened): `?lang=en` does (it was the old address of the English version, and the root `.htaccess` redirects it too), `?lang=pt` stays, then the visitor's saved choice (`localStorage` key `lang`, written when they click a language link, use the palette or answer the offer below), else they stay. The browser language sends no one ([0012](decisions/0012-no-redirect-by-browser-language.md)): on the Portuguese page, a browser whose first translated language in `navigator.languages` is English (any `en*`), with no choice saved and a user agent that is not a crawler, sees `LanguageOffer`, a note fixed under the header, in English on both pages, that offers the English page. Taking it switches like the header link; declining it saves pt-BR. The header has one link per language (`aria-current` marks the current one); a click switches in place and moves the address with `history.replaceState`, a click with a modifier key opens the other page.
- **Dictionaries:** `source/js/i18n/locales/pt-br.js` and `en-us.js` export one nested object each, with the same keys. Banco Central terms (SPI, DICT, Pix, pacs.008, Conta PI, ISPB, RSFN, EndToEndId…), company names and Kafka topics are not translated.
- **Markup contract** (`Translator.applyTo`): `data-i18n="key"` sets the text, `data-i18n-html="key"` sets inline markup (`<em>`, `<strong>`…), `data-i18n-attr="aria-label:key;title:key"` sets attributes (also `data-cursor`, `placeholder`). When a fragment shares its parent with other nodes, wrap it in `<bdi data-i18n="key">`: a neutral inline element that no descendant selector like `.panel span` can catch.
- **Text built by JS:** ask `translator.t('key', { name: value })` (`{name}` placeholders) or `translator.plural('key', count)` (`key.one` / `key.other`). Elements the JS creates carry `data-i18n` too, so a language change retranslates them for free. Anything computed from live data subscribes with `translator.onChange(...)` in its `mount()` and redraws. `translator.bind(element, key)` sets text and records the key in one call.
- **Numbers and dates:** `Formatter.use(locale)` runs first on every change; `Formatter.decimal`, `integer`, `clock`, `shortDate`… follow it. Clocks are 24-hour in both languages.
- **Editing copy:** change the dictionaries, then run `node tools/i18n-check.mjs --fix-html`. The pt-BR text inside `index.html` (shown before the JS runs, and what crawlers read), the `<title>` and the description and Open Graph tags are generated from `pt-br.js`, and `en/index.html` is generated from the result and `en-us.js` (language, canonical address, Open Graph locale, paths made absolute because the page is one folder down); without the flag the same command reports any difference as an error. After editing `index.html` itself, run it with the flag too, so the English page follows. Section heights change with the copy, the fonts and the layout, so after any of them run `node tools/measure-sections.mjs --write` (several minutes, `--help` lists the options), which rewrites the generated block in `css/foundation/layout.css`; the layout-stability E2E test fails while that block is out of date.
- **The legal pages** (`privacidade/`, `cookies/`, `termos/`, and `en/privacy/`, `en/cookies/`, `en/terms/`) are the exception to the dictionaries ([0014](decisions/0014-legal-pages-written-in-html.md)): each is a static HTML file written in its own language, linked to the same page in the other language by its address and `hreflang`. A change to one changes both files, with the same date at the top. `node tools/i18n-check.mjs --fix-html` copies the head script of `index.html` into them, because the Content-Security-Policy allows that script by one hash.
- **The 404 pages** (`404.html` and `en/404.html`) are written in HTML the same way ([0016](decisions/0016-a-404-page-of-our-own.md)). The server picks the language by the address: every missing address under `/en/` gets the English page, through the `ErrorDocument` of `en/.htaccess`, and every other one the Portuguese page. Each offers the home page of the other language.
- **Adding a key:** add it to both dictionaries, use it, run `node tools/i18n-check.mjs`. **Adding a language:** one dictionary file, one entry in `Dictionaries.BY_LOCALE`, one in `Locale.SUPPORTED`, plus the language in `LANGUAGES` of `tools/measure-sections.mjs`, then regenerate the section placeholders in `css/foundation/layout.css` (they hold one set of rules per language, under `:lang(xx)`).
- **Test:** open `/en/`; `eklund.setLocale('en')` in the console; headless detection with `--lang=pt-BR` in the `flags` of `tools/preview.mjs`. Lines already written to the load-test terminal keep the language they were written in.

## Which page a visitor gets

```mermaid
flowchart TD
  start["A visitor opens /"] --> query{"Does the address have ?lang"}
  query -->|"lang=en"| en["Goes to /en/"]
  query -->|"lang=pt"| pt["Stays on /<br/>Portuguese"]
  query -->|"no supported ?lang"| saved{"Saved choice<br/>in localStorage?"}
  saved -->|"en-US"| en
  saved -->|"pt-BR"| pt
  saved -->|"nothing saved"| stay["Stays on /<br/>Portuguese"]
  stay --> offer{"A person whose first translated<br/>language of navigator.languages is en*?"}
  offer -->|yes| note["Sees the offer of /en/"]
  offer -->|no| none["Sees no offer"]
```

The inline script in the head of `index.html` makes the choice of page before the first paint, and `LanguageOffer.wanted` decides about the offer once the scripts run. `tests/support/head-script.js` runs that script against a fake browser, so the table of cases in `tests/contract/head-script.contract.test.js` covers every branch of the script, and `tests/js/i18n/language-offer.component.test.js` every branch of the offer.
